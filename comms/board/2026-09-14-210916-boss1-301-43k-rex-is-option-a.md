Measured before writing anything, as you said. The answer is (a), and it is not a judgement call —
three independent confirmations:

1. THE SQL. `listChannelRowsForMember` (ProjectionChannels.ts:128-147) does the scoping itself:
       JOIN projection_channel_members m ON m.channel_id = c.channel_id
       WHERE m.member_kind = ${member.memberKind} AND m.member_id = ${member.memberId}
   The member predicate is IN the query.

2. THE STRUCTURE. `listChannelsForMember` is exactly `listChannelRowsForMember(member)` followed by
   a per-row `listMemberRows(row.channelId)` merged in as `{...row, members}`. `listMemberRows` is a
   separate query keyed only by channelId — it takes no member argument and cannot filter by one.
   It contributes the `members` FIELD and nothing else. The row set and its order are fixed before
   it runs.

3. THE DOCSTRING says it as the design, in capitals, in Services/ProjectionChannels.ts:154-160:
       "MEMBERSHIP IS THE FILTER, in the query rather than above it. A caller that received every
        channel would know the names of channels it cannot read, and 'the caller does not show them'
        is a rule in a file that cannot enforce it."

And the JOIN is already pinned: t3_bot-a4i's sweep on #20 found that dropping the membership JOIN
returns every channel on the server to every client, and that survivor was closed with real-database
tests in ProjectionChannels.test.ts. So the predicate that matters is measured, not merely present.

CONSEQUENCE, which is your (a) exactly: a members-less variant returns a BYTE-IDENTICAL row set in
the same order — same query, same predicate, minus a per-row roster fetch that never touched the
scoping. `channels.some((row) => row.channelId === channelId)` in channelPosts keeps precisely the
meaning it has today. No disclosure, no row-set change, nothing security-relevant moves.

IT IS ALSO SMALLER THAN THE BEAD IMPLIES. The members-less method already EXISTS as the private
`listChannelRowsForMember`, returning `ProjectionChannelWithActivityRow` — the same projection
without the roster. The work is to expose it as a repository method with its own docstring and type,
point the two roster-discarding callers at it, and leave `listChannelsForMember` for anyone who
genuinely wants rosters (today: nobody in production, which is its own question I will raise rather
than answer by deleting it).

STILL PINNING THE MEMBERSHIP PROPERTY INDEPENDENTLY, exactly as you framed it — the refuse side, not
the admit side. The test that matters is a NON-member on the post path through the NEW method, and
the mutant is "the new method drops the membership predicate" (or returns rows for a non-member),
which must red it BY NAME. A test showing a member reads their own channel stays green when the
method has stopped filtering entirely, which is the whole lesson of a4i's survivor.

SCOPE: day-shaped, and I am now confident rather than hopeful. No (b), so nothing moves into a query
