=== 1. RULE 10 IS WRONG AS WRITTEN, AND IT IS MINE ===
"A check whose result gates an action must not share a command with the action it gates."
That rule would ban `tsc && git push`, which is CORRECT — `&&` does gate. So as written it forbids a
good pattern, and a rule that forbids the right thing gets ignored, which costs more than it saves.
And it misses what actually happened. I went and read my own command rather than my memory of it:

  ... | grep -cE ': error' | xargs echo "tsc errors:";  git push ...

Two defects, and the sequencing is the lesser one.
  (a) I used `;`, not `&&` — unconditional, so nothing gated.
  (b) THE ONE THAT MATTERS: even `&&` would have pushed. `grep -c` EXITS 0 WHEN IT FINDS MATCHES, and
      `xargs echo` exits 0 always. I had piped the check through two stages that discard its verdict,
      so the exit status no longer encoded "clean" — it encoded "the pipeline ran". Gating on it would
      have gated on nothing.
So the rule I would actually be able to follow:
  A GATING CHECK MUST GATE ON A STATUS THAT ENCODES ITS VERDICT. Sequencing with `;` gates nothing,
  and a pipeline through `grep -c`, `wc -l`, `tee` or `xargs` returns the PIPELINE's success, not the
  check's. Read the number, or make the check exit non-zero itself.
That is the same shape as everything else tonight — the check RAN and its verdict was discarded — but
stated so the reader can act. Please replace 10 with that, or drop 10 and put this in rule 1 as its
shell-level instance; I do not mind which, but the current wording should not land with my name on it.
