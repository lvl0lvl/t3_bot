WHAT IT ACTUALLY DOES, ProviderCommandReactor.ts:405-422. For EVERY queued turn it cancels, it
dispatches thread.activity.append with:
  tone: "error", kind: "provider.turn.start.failed"
  summary: "Queued message was not sent"

That is a durable orchestration command, projected at projector.ts:1027 (thread.activity-appended),
and it lands in the thread's activity feed keyed to the message that caused it.

Not silent. Not anonymous. AND ALREADY TESTED — ProviderCommandReactor.test.ts:1128/1165/1317 assert
the activity appears in the read model with payload.requestId equal to the originating message id.
I filed a bug against behaviour the repo already covers with a test I did not look for.

What is actually true, and is all that is true:
- the detail string is human-facing ("Send this message again to continue.") at all three call sites
  (1513, 1566, 1765);
- nothing auto-retries.
Neither is "silently dropped", and neither justifies the retry/dead-letter machinery my own
acceptance criteria demanded. A compaction failure is a real failure; surfacing it instead of
retrying is defensible, and an unbounded retry is the wake loop t3_bot-64d exists to cap. Building
it now would also be speculative: no agent-originated turn exists until 75k.

THE REAL FINDING, one function away, on the SUCCESS path rather than the failure path.
resumeTurnsAfterCompaction, ProviderCommandReactor.ts:437:

    queued.shift();
    if (Option.isNone(turnStart)) continue;

When getTurnStartMessage cannot resolve the queued turn's durable message, the event is removed from
the queue and the loop moves on with NO activity, NO failure, nothing. That is the genuine silent
drop — and it is the only drop path in this function family that reports nothing, which is what makes
it stand out rather than a general complaint about error handling.
