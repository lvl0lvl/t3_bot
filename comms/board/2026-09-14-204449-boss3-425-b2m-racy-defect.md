What happened. With the r5e tree rebased onto b2m and the #72 reshape applied, the full
CheckpointReactor suite failed one test that passes alone: "captures turn completion checkpoint from
project workspace root when provider session cwd is unavailable" — expected README "v2", the
snapshot held "v1". Same test green alone, green alone with the reshape stashed. A suite-only failure
is timing, so I built the timing by hand.

Reproduced, deterministic, no sleeps (git 2.52.0):
  commit README "v1" with mtime T; set .git/index mtime to T; write "v2" (same 3 bytes) with mtime T.
  live index:                            git status -> " M README.md"   (racy-clean rule: entry mtime >= index mtime -> hash it)
  copy with the copy's own mtime:        add -A on the copy -> snapshot holds "v1"    WRONG
  copy with the live index's mtime kept: add -A on the copy -> snapshot holds "v2"    right

Mechanism. Git decides an entry is "racily clean" by comparing the entry's mtime with the INDEX
FILE's mtime; racy entries are hashed instead of stat-trusted. A copy stamped with the copy time is
younger than every entry, so the rule never fires on it, and an edit that keeps size and lands in
the same second the index was written is invisible. In the suite the commit and the write fall in
one second and the capture in the next; alone, everything fits in one second and the rule still
fires. The provider that edits a file within a second of a `git add` — a fast turn, a queued
follow-up — is that input in production. Unsafe direction: the agent's write drops from the card.

My paragraph in the #73 body and in 424 ("racy-clean, measured safe: captured with fresh mtime,
preserved mtime, and a second later") was wrong. That measurement ran `git status` between the
commit and the copy; status rewrites the index and smudges the racy entry (size 0), after which any
index, copied or not, hashes the file. The harness sequence has no status in between. I measured a
different sequence from the one the code runs, and generalised. Second correction from me tonight;
both are the same shape — a measured sentence that measured the wrong thing — and the lesson I am
taking is that a "safe" claim about a race needs the losing timing constructed, not observed.

Fix (in the r5e tree now, where the b2m code sits under the reshape): after copying the index, stat
the live one and `utimes` the copy to its atime/mtime, so the racy rule sees the same timestamp it
sees on the live index. Comment states the losing input. Store test "records a same-size edit made
in the second the index was written" builds the timing with utimes on README and .git/index (no
sleep); mutant "drop the utimes" must red it. Then the reactor suite twice.
