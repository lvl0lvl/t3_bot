THE BEAD SAID "something apps/desktop needs in a cold tree is not produced by pnpm install". That
framing is half right and the half that is wrong matters for the fix:

  electron@44.1.0's package.json has NO scripts block. Nothing for pnpm to run. `allowBuilds:
  electron: true` in pnpm-workspace.yaml is moot — there is no build to allow. Its own index.js
  fetches the binary LAZILY: on first `require("electron")`, if `path.txt` is absent, it spawns
  `install.js`, which downloads and unpacks Electron.app.

So in a fresh tree the first thing to require electron is a test worker — and vitest starts several.
Each sees no path.txt, each spawns install.js, and they collide unpacking the same directory:

  Error: failed to create directory '.../electron/dist/Electron.app/Contents/MacOS': File exists

The file the bead names loses that race and fails to LOAD. A "prepared" tree is simply one that has
required electron once before. That is why the same file passes 30/30 on a second run of the same cold
tree — by then one worker has won.

MEASURED, not read, on one cold tree at 2dcca0a7b with its own frozen install:

  cold electron -> suite                          FAIL DesktopBackendConfiguration.test.ts, 1 failed / 97 passed
  wipe dist + path.txt, run install.js ONCE, suite   98 passed, 4 skipped, 1260 tests  (the bead's numbers exactly)

And the first run, under three concurrent gate installs, failed FIVE files rather than one — the race
is load-dependent, which is why the bead saw one and I saw five and a second run sees none.

THE STEP FOR THE GATE: after `pnpm install --frozen-lockfile` in the base worktree, run electron's
install.js once, serially, before any suite. Not `pnpm rebuild electron` — there is nothing to
rebuild — and not a retry, because a retry that happens to win is the same race with better odds.
The exact form (pnpm exec vs. resolving the package path; whether it belongs in the gate or in a root
