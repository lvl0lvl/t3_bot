Taken while both senior tracks were dark, because it is a decision and not a build.

The short version. t3_bot-z5r asks "is forward-compatibility for unhandled event types retained
or revoked". Both answers assume the projector HAS that property. It does not.

Measured at ff1a5a347, all three:
1. The event union is 40 literals (OrchestrationEventType, packages/contracts/src/orchestration.ts
   :2017-2059), confirmed by running it, not by reading it.
2. Exactly six are uncased in projector.ts and they are exactly the six *-requested types the bead
   names. The seven other uncased names you will find by grep - starting, ready, running, idle,
   error, interrupted, stopped - are session-status literals in a NESTED switch. Do not count them;
   I nearly did.
3. The decisive one. Every persisted row is decoded through the closed union at
   apps/server/src/persistence/Layers/OrchestrationEventStore.ts:31, applied in readFromSequence at
   :304. A complete thread.turn-start-requested row decodes ACCEPTED; the byte-identical row with
   ONLY the type literal changed decodes REFUSED.

Point 3 is the ruling. The default branch cannot receive an unknown future type on the read path,
so the thing the catch-all is famous for is not a thing it does. And projector.test.ts:302, the
seven-month-old test named "keeps projector forward-compatible for unhandled event types", hands
projectEvent a CAST object - makeEvent ends "as OrchestrationEvent" at projector.test.ts:39 - so it
bypasses the decode boundary and pins a property production cannot produce. The name is what has
misled every reader, including this bead's first framing.

On method, since it is the repo's own rule: my first probe refused BOTH the unknown type and the
known one, because the payload was wrong, and it would have "proved" the ruling. It proved nothing.
The control - a known-uncased type that must decode ACCEPTED - is what makes the subject's refusal
mean anything. Ask what your assertion does when the subject is absent.

Ruling: runtime default RETAINED, forward-compat claim REVOKED, one change carrying (a) the six
types grouped as one fallthrough case with one comment, (b) a compile-time exhaustiveness assertion
on the default so a 41st event type is a type error until someone decides - that is the part that
would have caught the channel events nearly shipping unprojected, and a comment alone would not
have - and (c) a REWRITE, not a deletion, of projector.test.ts:302 under a name that says what it
actually pins. Criteria and the adversarial question are in the bead notes.

Split out as t3_bot-5yq (P2, not to be fixed before it is ruled): the store REFUSES an unknown type
and fails the whole read, so a build cannot read a log written by a newer build. Downgrades and
rollbacks produce exactly that input. That is the real forward-compatibility question and it sits
one layer below the projector.
