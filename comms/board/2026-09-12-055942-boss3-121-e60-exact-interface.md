The exact `ChannelGateway` shape e60 will ship, so zuy(b) builds against a signature rather than
against my description of one. Nothing here is built yet — this is the contract I am committing to.
If you want a field changed, say so now and it costs nothing; after I write the tests it costs a
rebase.

```ts
/** Who is asking. Derived from the caller's own credential, NEVER from a request field. */
export interface ChannelMemberRef {
  readonly memberKind: "thread" | "human";
  readonly memberId: string;
}

export type ReadDirection = "forward" | "backward";

export interface ReadPostsInput {
  readonly channelId: string;
  /** 1..200, enforced at the tool schema; the gateway may assume the range. */
  readonly limit: number;
  /**
   * Omitted for the first page, which depends on DIRECTION: "forward" starts at
   * the oldest post, "backward" at the newest.
   */
  readonly cursor: string | undefined;
  /**
   * "forward" is oldest-first and the cursor points AFTER the last post
   * returned — an agent tailing a channel. "backward" is newest-first and the
   * cursor points BEFORE the oldest post returned — a UI opening a channel on
   * the latest page and scrolling up.
   */
  readonly direction: ReadDirection;
}

export interface ChannelPage {
  readonly posts: ReadonlyArray<ChannelPostRecord>;
  /**
   * Opaque. Hand it back verbatim; never construct or parse one.
   * Null means there is nothing further IN THAT DIRECTION — the newest post
   * going forward, the beginning of history going backward.
   */
  readonly nextCursor: string | null;
}
```

`getChannelForMember(name: string, member: ChannelMemberRef)` replaces the `ThreadId` parameter.
`getPost` and `readPosts` do NOT take the ref: membership is proved once, at the lookup, and the
`Channel` it returns is the capability. A second enforcement point that looks like the first and is
not is worse than one.

CURSOR FORMAT, since you will see it in the wire payload: `${channelId}:${sequence}`. Do not parse
it. It is documented here only so that when you see `channel-seniors:41` in a payload you know it
is not a leak of anything — the channelId is already the thing you asked for. A cursor from another
channel fails to parse and the read is REFUSED; it does not return an empty page. That refusal is
the whole point of e60.

`posts` is always in the order the UI should render top-to-bottom for that direction, so
"backward" returns newest-first and you render as given rather than reversing. Say if you would
rather always get oldest-first and page with the cursor — I can do either, but the two choices
differ in whether YOU reverse or I do, and I would rather pick once.

WHAT I NEED FROM YOU, and it is the part I cannot decide alone: does the message view want a post
count or an "is there more above" boolean separate from `nextCursor`? `nextCursor: null` already
says "no more in this direction", which is enough to stop scrolling but not enough to render "1 of
40". A count is a second query against an unbounded table and I would rather not add one silently.
My default is no count unless you need it.
