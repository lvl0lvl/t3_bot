MILESTONE 2 INPUT — "a turn's diff starts from the tree the turn found" (t3_bot-r5e), and the
capture cost that blocked it (t3_bot-b2m, closed). 2026-09-14, boss3. Nothing here is built.

THE PROBLEM, one sentence. Several threads share one checkout and main merges between their turns;
a diff from the previous checkpoint (turn/N-1) lists other writers' changes as the turn's. Fixing it
needs "the tree the turn found", and that tree is a fact only at the instant the provider is handed
the turn — behind any queue it is a guess (the CI-red multi-turn test: the adapter wrote before any
start signal reached the checkpoint reactor).

THE CONSTRAINT SET. Any option must survive these; each was found by constructing the input, and each
records the WRONG content for a file the turn edited unless marked otherwise.
 1. Index flags. assume-unchanged and skip-worktree tell `git add -A` not to read the file. Input:
    `git update-index --assume-unchanged f; edit f; capture` -> old content. Both bits on one entry
    print as lowercase `s`; a non-UTF-8 path (Linux) cannot be spelled back to git by a decoded string.
 2. Stat-cache timing (racy-clean). Git hashes an entry only if its mtime is not older than the index
    FILE's mtime; a copy with a fresh mtime disarms that. Input: same-second, same-size edit, built
    with utimes (a `git status` in the probe smudges the entry and hides the defect).
 3. Index membership. A copied index contributes WHICH paths exist, not only stat data. Inputs:
    `git add -f .env` (ignored, force-staged) -> captured and shipped as "+AWS_SECRET_ACCESS_KEY=" in
    the turn diff over the WebSocket (this one leaks, it does not merely mis-attribute);
    `git rm --cached x; ignore x; edit x` -> recorded deleted; a merge conflict outside the capture
    directory -> write-tree exit 128 on every turn until resolved; a staged edit outside the capture
    directory -> recorded from the index instead of HEAD; core.splitIndex -> a sharedindex.* written
    into the user's .git per capture, the referenced one deleted under a short expiry.
 4. The guard reading a prefix. The flag listing at the process runner's default 1,000,000-byte
    SILENT truncation cap; this repository lists at 1,571,002 bytes, so a flagged entry sorting past
    the cut is invisible to the check that exists for it. Found by two blind verifiers independently.
 5. The meta-constraint. Every one of 1-4 was the USER's index contributing something (flags, timing,
    membership, extensions) to a snapshot that was meant to take only its stat cache; the checks
    added to bound the unknowns were themselves subject to one. The bar the PM set — one more
    unsafe-direction defect and the optimisation is dropped — held, and it should be set in advance
    again for any option below that reads user state.
 Numbers to beat (this repo, 21,665 files, git 2.52.0): fresh capture 1.5 s warm / 2.4 s cold, of
 which `add -A` is all but ~50 ms; a stat-cache-seeded capture 140-288 ms. Real cone-mode sparse
 checkouts were unaffected by either seeding (git add is sparse-aware). Upstream has three attempts
 at the seeded index (#8538 closed, #10725 and #10792 open, same region) — whichever lands, the
 fork rebases into it.

THE OPTIONS.

(A) ATTRIBUTE BY TOOL EVENTS — no snapshot. The card lists turn/N-1..turn/N restricted to the paths
 the turn's tool events touched (Claude Write/Edit, Codex apply_patch). Other writers excluded by
 path, not by time.
 User cost: zero latency; correctness in the UNSAFE direction for every write that is not a tool
 event — formatters, codemods, `git checkout --`, `sed -i` through a shell tool. This repo's own
 pre-commit runs `vp fmt`; agents here run it constantly. Under-reports the routine case.
 Build cost: low (an event-to-path map per adapter; six adapters, a decision each).
 Falsifier: a turn whose only edit is a formatter run; the card must show the file and cannot.
 Status: REFUSED for M1 on exactly that input (board 313). Recorded so it is not re-proposed as new.
 Unknown: whether the shell tool's stdout could be parsed for written paths reliably enough to close
 the gap — I doubt it, and it would be a heuristic with its own unsafe direction.

(B) A T3-OWNED PER-THREAD INDEX — never read the user's index. Build our own index file per thread
 once (read-tree HEAD + add -A, 1.5 s, at thread start, off the turn path); each capture reuses OUR
 file: `read-tree --reset HEAD` (follows HEAD; measured to keep the stat cache), then `add -A`.
 User cost: ~150-300 ms per capture (the seeded numbers, since the stat cache is what they measured);
 disk: one index file per thread in the git common dir (~2 MB on this repo); correctness: of the five
 classes, 1, 3 and 4 cannot occur (no user flags, no user membership, no listing needed because no
 flags are possible); 2 remains and is ours to stamp (the utimes fix, with its constructed test);
 split index/fsmonitor/untracked cache are ours to disable.
 Build cost: medium — a per-thread file to create, locate, invalidate on thread delete and on
 corruption, and to garbage-collect; a second capture path to keep equal to the first.
 The bar, set in advance (board 313): state what the T3 index contributes that HEAD does not. Answer:
 only stat data for entries whose blob equals HEAD's, plus untracked files' absence — and stat data
 is exactly class 2. So the falsifier is the racy fixture: a same-second same-size edit after OUR
 last write of the file must be captured; and a second one: an entry whose stat data in our index is
 stale because the file was replaced with identical size and mtime by a tool that preserves them
 (rsync -t, cp -p) — git itself misses that on the live index, so the honest claim is "as correct as
 git status", stated as a limit.
 Unknown: whether a stale T3 index (thread idle for days, HEAD moved far) makes `read-tree --reset`
 plus `add -A` slower than fresh; and whether two captures for one thread can ever run concurrently
 (a start snapshot and a completion capture) and race on one file — needs a lock or two files.
 Status: not ruled; carries the same "constructed inputs before it ships" burden as the dropped one.

(C) FILESYSTEM CLONE (APFS clonefile / reflink) as the start snapshot, hashed at completion.
 User cost: O(files) syscalls before the send (unmeasured; likely 100-300 ms on 21k files); disk:
 copy-on-write until the turn writes; correctness: a real point-in-time copy, none of classes 1-4.
 Build cost: medium, platform-split.
 Falsifier: a Linux host on ext4 — no reflink, so either a full copy (seconds, disk) or the 1.5 s path.
 Status: REFUSED (board 313): "remote ready" on Linux hosts is a product invariant (AGENTS.md,
 "Remote ready"; `npx t3` on a server is a supported host).

(D) ASYNC CAPTURE WITH RACE DETECTION — keep the snapshot shape, move it off the turn path. Fork the
 capture at sendTurn; the provider starts immediately; at completion, decide whether the snapshot
 lost the race and, if so, mark the card "base unknown" (diff from turn/N-1 with a badge) rather than
 present a wrong base.
 What "detect a lost race" would have to measure: for each path the completion diff lists, whether
 the snapshot's recorded stat (mtime/size/inode from the capture's `add -A`) predates the provider's
 first write to that path — which needs the provider's first-write time per path (tool events give
 it for tool writes; shell writes give nothing, back to (A)'s gap) OR a conservative rule: any path
 whose snapshot stat is not older than the capture's own start time is "uncertain". The conservative
 rule over-reports uncertainty on a fast provider (Codex acknowledged in 0.5-1.1 s here, the capture
 takes 1.5 s: on this repo the race is lost more often than won, so the badge would be the norm).
 User cost: zero latency; correctness safe (uncertain is stated, never silently wrong) but the
 feature degrades to a badge exactly on the large repos it was for.
 Build cost: high — design work on the reactor seam, a new card state, the per-path timing model.
 Falsifier: a provider whose first write lands before the capture's own start timestamp is taken
 (the adapter's queue is faster than the fork) — then "uncertain" is wrong in the unsafe direction.
 Unknown: whether the badge is a product the maintainers accept ("a lying spinner" is in AGENTS.md's
 list of things users notice; a card that says "base unknown" on most turns may be worse than the
 stale card it replaces).

(E) SEEDED THREADS STOP SHARING THE MAIN CHECKOUT — each seeded thread gets its own worktree, nobody
 else writes to it, so turn/N-1 IS the tree the turn found and no snapshot, index, listing or race
 exists. Applies the generalising rule to the bug rather than to the capture.
 User cost: disk (a worktree per seeded thread — on this repo a checkout is ~200 MB before
 node_modules; with `pnpm install` per worktree, ~1 GB and 25 s each); latency: none per turn;
 correctness: by construction, none of classes 1-5.
 Build cost: low-to-medium — the worktree lifecycle exists (lanes, EnterWorktree, the thread
 worktree path is already a thread field); seeding would create per-thread worktrees instead of
 pointing threads at one checkout; cleanup on thread delete already exists for lane worktrees.
 Why it might be wrong, argued: (i) the shared checkout is the FEATURE for some threads — a team of
 agents editing one tree on purpose (channels, "seeded threads share one checkout" is how the
 comms layer was designed; the merges between turns are not noise, they are the collaboration) —
 for those threads the diff question is real and (E) removes the collaboration, not the bug;
 (ii) installs per worktree cost 25 s and a gigabyte each on this repo, and a thread that is
 seeded and never spoken to pays it for nothing; (iii) a turn that must see another thread's work
 needs a merge into its own worktree, which is exactly a between-turn write, so the problem returns
 as a merge step the user now has to ask for.
 Falsifier: one seeded-thread flow in the product design that REQUIRES two threads to see each
 other's uncommitted edits in one tree; if that flow exists, (E) is a no. I do not know whether it
 does — the PLAN.md's channel design is the place to check, and it is the PM's document.
 Unknown: whether the "10 changed files" stale card the bead describes is even observed on threads
 that would get their own worktree, or only on the shared ones — if only shared, (E) fixes the
 threads that do not have the bug.
 Status: the only option that deletes the problem; the argument against it is a product one, not a
 mechanism one, and belongs in the plan beside (B) and (D).

WHAT I WOULD DO, stated once: check (E)'s falsifier in the plan first — it is a reading, not a
build. If seeded threads are meant to collaborate in one tree, (E) is out and the choice is (B)
with its bar versus (D) with its badge; I would then take (B), because it contains the problem to
one class (2) that has a constructed test, and set the bar in advance as: any input where the T3
index reports a file as unchanged that git status on the live index would report as modified.
