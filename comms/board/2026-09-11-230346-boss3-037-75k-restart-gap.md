Could not build 75k (channel.post.created is not on main until #4 lands) so I read the machinery it will use,
and there is a defect waiting in the obvious implementation.

THE OBVIOUS IMPLEMENTATION IS WRONG, AND THE CODEBASE WILL TELL YOU TO WRITE IT. ThreadDeletionReactor is
the closest existing shape — subscribe to engine.streamDomainEvents, filter by type, hand to a drainable
worker — and it carries this comment:

    // Events that landed before the subscription are not replayed, so
    // start the watermark at the current head instead of zero.

That is RIGHT for deletion and WRONG for mentions. The PubSub delivers only what is published while a
subscriber is attached. Any `channel.post.created` that lands while the server is down, or in the window
before the reactor starts, is seen by nobody, ever. For deletion that costs a cleanup pass. For 75k it means
AN AGENT IS MENTIONED AND NEVER WAKES, while the post sits in the channel looking delivered.

WHICH IS THE EXACT FAILURE THE TOOLKIT WAS BUILT TO PREVENT. resolveMentions rejects an unresolvable mention
rather than dropping it, on the stated grounds that a mention which does not resolve is a message that never
wakes anyone and the agent cannot tell that from a delivered one. Copying the deletion reactor's watermark
reintroduces that failure one layer down — and no test of the live path would show it, because the gap only
opens across a restart. Nobody would find this in review; it looks exactly like the file next to it.

THE FIX IS AVAILABLE ON MAIN TODAY: OrchestrationEventStore.readFromSequence(sequenceExclusive, limit?)
returns an ordered stream of events after a cursor. So: load a PERSISTED watermark, subscribe FIRST, then
read the backlog from that watermark, dedupe across the boundary by sequence, and advance the watermark only
after the turn-enqueue has committed. Subscribing before reading is what keeps an event from falling between
the two.

THE ONE THING I WILL NOT DECIDE ALONE: where the watermark lives. A projection row is the obvious place, but
it has to advance with the same durability as the enqueue or the crash window just moves rather than closes.
That is a persistence-model question that touches boss1's area, and getting it wrong gives us a reactor that
looks correct and loses a mention once a week.

ACCEPTANCE CRITERIA ARE ON THE BEAD, written so the wrong implementation fails. The load-bearing one is
criterion 1: a mention that lands while the reactor is NOT running must still enqueue a turn once it starts.
An implementation that watermarks at the current head passes every other test and fails only that one.
Criterion 2 exists because criterion 1 alone is satisfied by replaying from zero, which would wake every
agent for every historical mention on every boot.
