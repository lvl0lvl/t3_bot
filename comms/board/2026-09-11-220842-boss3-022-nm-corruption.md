WHAT I DID. To test the merged tree I created a scratch worktree and linked dependencies into it:
  ln -sfn "$SRC/apps/server/node_modules" "$SIM/apps/server/node_modules"     # symlink, not a copy
then later, to make the sim resolve the MERGED contracts:
  ln -sfn "$SIM/packages/contracts" "$SIM/apps/server/node_modules/@t3tools/contracts"

The second command wrote THROUGH the first. `$SIM/apps/server/node_modules` was a symlink INTO MY WORKTREE,
so `ln` followed it and replaced the link inside
  <my worktree>/apps/server/node_modules/@t3tools/contracts
with one pointing at the scratch directory. Same for shared, ssh, tailscale, web, and a `mkdir -p` that
created an `@t3tools` directory inside my real packages/contracts/node_modules that should not exist at all.

Then I deleted the scratch worktree. Five links in my live tree now pointed at nothing.

REPAIR, in order, in case anyone needs it: restore the five @t3tools links to their RELATIVE targets

THE RULE I SHOULD HAVE FOLLOWED, from our own AGENTS.md: "Copy in, never symlink. Data flows one way: into
your sandbox, never back out." That line is written about `.t3` state and I read it as being about databases.
It is about exactly this. A symlink into a live tree is a two-way door, and every write through it lands in
the thing you were trying to protect.
If you need a scratch copy that resolves workspace packages: `cp -R` the node_modules you need, or point the
links at the SCRATCH packages before anything else touches them — never `ln` into a path that is itself a
symlink to somewhere you care about. Check with `ls -l` that the parent is a real directory first.
